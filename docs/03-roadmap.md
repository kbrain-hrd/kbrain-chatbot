# 구현 계획

## 기술 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 언어·환경 | Python + `uv` | 가상환경 필수 |
| 백엔드 | FastAPI | 유선 UI·시트 경로가 같은 백엔드 사용 |
| **유선 대응 UI** | **웹 (FastAPI 서빙)** | 담당자 여러 명 — CLI 부적합 |
| 시트 연동 | Google Sheets API + Apps Script 트리거 | 질문 입력 즉시 감지 |
| PDF 추출 | **pypdfium2** (대조군 pdfplumber) | pdfplumber 단독은 숫자 누락 — [05](05-data-survey.md) 3장 |
| 문서 | PDF → 마크다운 | 변환 검증 포함 |
| 검색 | **벡터 미사용.** 앵커 기반 특정+조회 | 문항 100개 규모라 목록 전체가 컨텍스트에 들어감 |
| 임베딩 | 사용 안 함 | |
| 답변 생성 | Claude Opus 5 (`claude-opus-5`) | |
| 코드 문제 검증 | 코드 실행 | 추론이 아닌 실측 |
| 알림·승인 | 슬랙 | 초안 카드 + 승인/반려 버튼 — [04](04-open-questions.md) 2-1 |

### 벡터 검색을 쓰지 않는 이유

단답 문항이 100개(2과목 × 5세트 × 2등급 × 5문항)뿐입니다.
전체 문항의 앵커·질문 요약 목록이 수천 토큰이면 컨텍스트에 다 들어갑니다.

목록을 통째로 주고 문항을 특정한 뒤 해당 파일을 로드하면,
**무엇을 근거로 답했는지가 로드 시점에 확정**됩니다.
벡터 검색은 문서를 조각내 "유사한 조각"을 가져오므로 출처가 흐려지고 문맥이 잘립니다.
출처 명시가 이 시스템의 핵심 요구사항이므로 조회 방식이 더 적합합니다.

운영 자료는 문항 구조가 없어 별도 판단이 필요하지만,
핵심 자료(준비안내·CBT가이드)가 크지 않아 섹션 앵커 조회로 시작합니다.

## 폴더 구조 (안)

```
kbrain-chatbot/
├── backend/
│   ├── ingest/        # PDF·hwpx·HTML → 마크다운, 추출기 대조 검증
│   ├── search/        # 앵커 카탈로그, 문항 특정 + 조회
│   ├── answer/        # 블라인드 풀이, 코드 실행 검증, 대조, 초안 생성
│   ├── web/           # 유선 대응 웹 UI (FastAPI 라우트 + 프론트)
│   ├── sheets/        # 구글시트 연동
│   └── slack/         # 승인 카드 발송, 버튼 콜백 처리
├── content/
│   ├── selfstudy/     # 등급/세트/과목별 마크다운 + 첨부
│   └── operations/    # 운영 자료 마크다운
├── raw/               # 원본 PDF·hwpx·zip (git 제외)
├── eval/              # 골드셋, 정확도 측정
├── docs/
└── README.md
```

`backend/ingest` → `search` → `answer` 가 **두 경로가 공유하는 코어**이고,
`web` / `sheets`+`slack` 은 그 위에 얹히는 출력부입니다. 갈라지는 것은 마지막 단계뿐입니다.

### 앵커 스킴

```
G-S01-M02-Q03   그린 · 1세트 · 2과목 · 3번 문항
B-S05-M01-Q01   블루 · 5세트 · 1과목 · 1번 문항
OPS-준비안내-응시환경   운영 자료 섹션
```

그린과 블루는 세트명·주제가 같아도 **문제와 정답이 다릅니다.**
등급이 앵커에 없으면 엉뚱한 정답을 근거로 답하게 되므로 필수 항목입니다.

## 단계별 계획

각 단계는 **검증 조건을 통과해야 다음으로 넘어갑니다.**

**1~4단계는 두 경로의 공통 코어**입니다. 유선이든 시트든 여기까지는 똑같이 필요합니다.
경로가 갈리는 것은 5단계부터이므로, 그전까지는 순서를 고민할 필요가 없습니다.

### 1단계 — PDF → 마크다운 변환 (90개 PDF)

- pypdfium2로 문제지·해설·답안지 변환
- pdfplumber로 동일 추출 후 **두 결과 대조 → 불일치 지점 리포트**
- 불일치 지점만 사람이 원본과 확인
- **재실행 가능하게(멱등) 작성** — 자료가 계속 추가되므로 일회성 스크립트로 만들지 않습니다

**완료 조건:** 대조 리포트의 모든 불일치 항목 확인 완료. 정답 숫자 누락 0건.
동일 입력으로 재실행 시 산출물이 동일할 것.

### 1.5단계 — 정답 검증 (부수 산출물, 선행 가능)

챗봇과 독립적으로 **지금 바로 착수 가능**하며, 그 자체로 쓸 수 있는 결과물입니다.

- 2과목: 해설의 정답 산출 코드를 첨부 CSV로 실제 실행 → 답안지 숫자와 대조
- 1과목: 첨부 문서에서 정답 근거를 재확인
- 불일치 건을 **기존 자료 오류 후보 목록**으로 산출

세트 간 비교는 하지 않습니다. 각 세트는 독립적으로 판정합니다.

**완료 조건:** 그린·블루 전 세트 1·2과목 대조 완료. 불일치 목록 산출.

### 2단계 — 문항 단위 분리 및 앵커 부여

- 문항 단위 분리, 앵커 부여 (`G-S01-M02-Q03`)
- 앵커 카탈로그 생성 (앵커 + 질문 요약 + 정답 형식)
- 운영 자료 섹션 앵커 부여

**완료 조건:** 100문항 전부 앵커 부여. 누락·중복 0건. 카탈로그가 컨텍스트 예산 내.

### 3단계 — 질문 분류 + 문항 특정

- 문제 관련 / 운영 관련 / 분류불가 판정
- 등급(그린·블루) 판별 포함 — 질문에 등급이 없으면 되묻기
- 앵커 카탈로그 기반 문항 특정

**완료 조건:**
- **문항 특정 정확도 ≥ 99%** (등급 오판 포함해서 측정)
- 등급 불명 시 추측 없이 되묻는 동작 확인

### 4단계 — 초안 생성 + 검증 게이트

- 블라인드 풀이 → 해설·답안지 대조
- 2과목은 코드 실행 결과를 풀이 근거로 사용
- 3과목은 루브릭 안내 경로 (별도 — [04](04-open-questions.md) 2-3)
- 플래그 판정 (해설불일치 / 근거부족)

**완료 조건:** 실제 질문 30건 이상으로 초안 품질 확인. **오답을 확신 있게 제시한 건수 0.**

### 5단계 — 유선 대응 웹 UI

전화받는 중에 쓰는 화면입니다. **구글시트 없이도 동작하므로 시트 미수령 상태에서 진행 가능**하고,
완성 시점에 그대로 실사용에 들어갑니다.

- 질문 입력 → 초안 + 근거(문항 원문·해설 인용) + 플래그를 한 화면에 표시
- 검수 완료된 답변 우선 조회 → 없을 때만 실시간 생성 ([01](01-design.md) 5장)
- 근거를 접지 않고 바로 보이게 — 담당자가 통화 중에 판단해야 합니다

**완료 조건:** 실제 질문으로 왕복 동작 확인. 검수 완료본 조회 시 즉답.
근거 없이 답을 표시하는 경우 0건.

### 6단계 — 구글시트 연동

- 질문 입력 감지 → 초안 기록
- 상태 전이 처리

**완료 조건:** 질문 감지 → 초안 기록 왕복 동작 확인.

### 7단계 — 슬랙 승인 흐름

- 초안 전문 + 근거 + 플래그 + [승인] [반려] + 시트 링크를 담은 슬랙 카드 발송
- 슬랙에서 승인 → 시트에 최종답변 자동 등록, 상태 `완료`
- 수정이 필요하면 시트 링크로 이동 → 수정 후 승인 ([04](04-open-questions.md) 2-1)

**완료 조건:** 승인 → 등록 흐름 정상 동작. 실사용자 테스트 통과.

## 검증 기준

| 항목 | 기준 | 이유 |
|---|---|---|
| 문항 특정 정확도 | ≥ 99% | 틀리면 이후 처리가 전부 무의미 |
| 등급(그린·블루) 판별 | ≥ 99% | 같은 세트명·다른 정답이라 혼동 시 오답 직결 |
| 변환 시 정답 숫자 누락 | **0건** | 정답지에서 숫자가 사라지면 근거가 무너짐 |
| 확신 있는 오답 | **0건** | 가장 위험한 실패 유형 |
| 초안 무수정 승인률 | 측정 | 자동화 확대 판단 근거 |
| 유선 응답 시간 | 측정 | 통화 중 사용이라 지연이 곧 실패. 검수 완료본 조회는 즉답 |

**못 답하는 것은 허용, 틀린 답을 확신 있게 제시하는 것은 불허.**

## 비용 개산

실제 문서 크기를 확인한 뒤 재산정한 값입니다.
모델은 Claude Opus 5 (`claude-opus-5`) — 입력 $5 / 출력 $25 per 1M tokens 기준.

### 문서 실측 크기

| 문서 | 텍스트 분량 |
|---|---|
| 문제지 1건 | 약 1.3~5.2KB |
| 해설 1건 | 약 1.5~3.7KB |
| 답안지 1건 | 약 1.0~2.1KB |

한 문항에 답하기 위해 로드하는 양은 **한 과목 단위(문제지+해설+답안지) 약 4~11KB**입니다.

### 질의 1건당 (문제 관련)

- 입력: 앵커 카탈로그 + 해당 과목 문서 + 프롬프트 → 대략 6~12K 토큰
- 출력: 초안 + 대조 결과 → 대략 1~2K 토큰
- **대략 건당 100원 내외**

### 프롬프트 캐싱

앵커 카탈로그(전 문항 목록)는 모든 질의에서 동일하므로 캐싱 대상입니다.
Opus 5의 최소 캐시 가능 길이는 **512 토큰**이라 카탈로그 크기면 충분히 걸립니다.
캐시 읽기는 입력 정가의 약 10% → 반복 질의에서 입력 비용이 크게 떨어집니다.

캐싱이 깨지지 않으려면 카탈로그를 프롬프트 **앞쪽에 고정**하고,
질문·날짜 등 매번 바뀌는 값은 뒤쪽에 두어야 합니다.

### 변수

- 독립 다중 풀이(같은 문제를 여러 번 풀어 대조) 적용 시 배수 증가
- 2과목 코드 실행 검증은 로컬 실행이라 API 비용 없음
- 운영 질문은 근거가 짧아 더 저렴
- 유선 경로에서 **검수 완료본이 조회되면 API 호출이 아예 없습니다** — 반복 질문이 쌓일수록 평균 단가 하락
